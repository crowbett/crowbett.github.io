# Demo contract

A demo is three things: a bridge in the project repo, a UI in this repo, and a lock entry tying them to one commit.

## Bridge (project repo, `cmd/webdemo/`)
- `main.go` is `//go:build js && wasm` and only wires the bridge: set `globalThis.__demo = func(method, paramsJSON string) string`, call `globalThis.__demoReady()`, then `select {}`.
- A `stub.go` tagged `//go:build !(js && wasm)` holds a `main` that prints "runs only as js/wasm" and exits 2; without it the package has no `main` on native platforms and the project's `go build ./...` / `go vet ./...` fail.
- All logic lives in a file without build tags (e.g. `handler.go`: `func Handle(method string, params []byte) any`) with a normal `handler_test.go`, so the project's own gate runs it on every commit.
- It calls the project's real packages (internal ones are fine: `cmd/webdemo` is inside the module). Never reimplement project logic in the bridge; the point is that visitors run the shipped code.
- Results are JSON objects. Errors are `{"error": "..."}`; a successful result must not have a top-level `error` key.
- Deterministic: anything random takes a seed from params. No wall clock: pass simulated time in params, or give the engine a simulated clock in the bridge (kvlite's `WithClock`). No network.
- Files: the worker loads `web/assets/memfs.js`, an in-memory Node-style `fs` that Go's js/wasm `os` package calls into, so an engine that writes files runs unchanged. It has `/` and `/tmp`, the working directory is `/`, and it lives as long as the worker (a reload starts empty). There are no file locks. Calls complete synchronously, and Go on wasm runs goroutines cooperatively on one thread, so code that spins waiting on another goroutine without blocking starves.
- Bounded: one call does at most ~50 ms of work on a laptop. Long runs are many calls (`step`, `run {ticks: n}` with a cap). State between calls is fine and lives in Go.
- Small: import only what the demo needs. `fmt` and `encoding/json` are fine; gRPC and database drivers are not. Avoid `net/http` (a probe of it plus `internal/rfc9111` gzipped to 1,819,664 bytes against 1,217,580 for the json-only smoke binary, measured) unless the project's own API is built on it, as edgecache's engine is; `regexp` added ~130 KB gzipped to edgecache's bridge (measured), so hand-check simple formats.

## Rust bridge (project repo)
A Rust demo is a `cdylib` crate (e.g. `crates/webdemo`) built for `wasm32-unknown-unknown` with no wasm-bindgen; `wasm/smoke-rs` in this repo is the reference. The same rules hold: real crates only, JSON in and out, `{"error"}` for errors, deterministic, bounded, small.
- It imports nothing and exports `memory` plus three functions (prefixed so they cannot clash with C's `malloc`/`free` in a linked library). `demo_alloc(len) -> ptr` returns `len` bytes the worker writes into, and traps if memory cannot grow. `demo_call(method_ptr, method_len, params_ptr, params_len) -> ptr` returns a buffer holding a 4-byte little-endian length and then that many bytes of UTF-8 JSON. `demo_free(ptr, len)` takes back a buffer from `demo_alloc` (with its `len`) or from `demo_call` (with length + 4). All three use alignment 1. The worker ignores any other export (a cdylib also exports every `#[no_mangle]` function, such as the C-facing ones codegraph's bridge defines for SQLite).
- The worker tells the kinds apart by the module's imports (a Go binary imports `gojs`; Rust and C++ modules import nothing), so the page and the lock need nothing else at load time.
- A panic aborts, which traps; the worker logs the trap to the console, reports "the demo crashed" and refuses further calls, as for Go. Set `panic = "abort"` in the release profile, or rely on `wasm32-unknown-unknown` aborting by default when the workspace profile must keep unwinding for another target (strata's UniFFI library).
- Put the logic in a plain function (`handle(method, params) -> serde_json::Value`) with normal tests, so the project's own `cargo test` covers it.
- The lock entry has `"kind": "rust"` and `pkg` is the crate's directory. `cmd/wasm` runs `cargo build --release --locked --target wasm32-unknown-unknown` there with the toolchain rustup picks from the repo's `rust-toolchain.toml` (required; it adds the target if missing), into a scratch target dir. It drops every `CARGO_*` (except `CARGO_HOME`) and `RUST*` (except `RUSTUP_HOME`) variable from the environment, replaces any `rustflags` from cargo config, and remaps the checkout and its siblings, the target dir, cargo home and the sysroot (rust-src installed or not) so no local path is embedded and the binary does not depend on where it was built. Pinned repos are exported to the fixed path `/tmp/crowbett-wasm/<slug>` (one build per slug at a time, under a lock): cargo hashes a path dependency outside the building workspace by its absolute path into symbol names, so keel-web (a one-crate workspace over sibling crates) built from a random temp dir gave a different binary on every build (measured, D8). Known limit: a `[profile.release]` in a cargo config file (`~/.cargo/config.toml`, or a `.cargo/` above the checkout) still applies. The lock records `rustc -V`. Building needs rustup (Homebrew's cargo is ignored); CI only checks hashes.

## C++ bridge (project repo)
A C++ demo is a directory of sources (e.g. `webdemo/`) built for `wasm32-wasip1` and exporting exactly the Rust bridge's ABI (`memory`, `demo_alloc`, `demo_call`, `demo_free`, same signatures, alignment 1), so the worker runs it as it runs a Rust module. raytracer's `webdemo/` is the reference. The same rules hold: real project code only, JSON in and out, `{"error"}` for errors, deterministic, bounded, small.
- It imports nothing. `cmd/wasm` fails the build on any import or a missing export, so a stray `printf`, `std::cout`, clock or `random_device` is caught before it ships rather than as a link error in the browser. In practice: export with `__attribute__((export_name("demo_call")))`; define `operator new`/`delete` over `malloc` and trap on failure; define `std::__libcpp_verbose_abort` to `__builtin_trap()` (libc++'s checks would otherwise print to stderr); there is no crt1, so call `__wasm_call_ctors()` once before first use. A trap is reported as a crash, as for Rust.
- Single-threaded: Pages cannot send COOP/COEP, so there is no `SharedArrayBuffer` and no `std::thread`. Keep `<thread>` out of the bridge's includes (raytracer's tile renderer lives in a header without it).
- Put the logic in a header with no platform code (`bridge.h`: `handle(method, params) -> std::string`) and test it natively from the project's own gate (`*_test.cpp` in the same directory, built by the project's CMake). Keep JSON hand-rolled: raytracer's flat-object reader and writer is 269 lines, and its whole module 280,179 bytes (112,204 gzipped).
- The lock entry has `"kind": "cpp"` and `pkg` is the directory. `cmd/wasm` compiles every `.cpp` directly in it except `*_test.cpp`, in one `clang++` from wasi-sdk with `--no-default-config --target=wasm32-wasip1 -std=c++20 -O3 -DNDEBUG -fno-exceptions -fno-rtti -nostartfiles -Wl,--no-entry -Wl,--strip-all`, so includes resolve relative to the sources (`#include "../src/camera.h"`) and no include path is configured. It drops `CPATH`, `*_INCLUDE_PATH`, `SDKROOT`, `CCC_*`, `CLANG*` and `C*FLAGS`/`LDFLAGS` from the environment and remaps the checkout and the SDK (`-ffile-prefix-map`), so the binary does not depend on where it was built (measured: an export to a different directory gave the same sha256). The SDK is pinned: `make wasi-sdk` (`scripts/wasi-sdk.sh`) downloads wasi-sdk 34.0, checks its sha256 and unpacks it to `~/.cache/crowbett-wasm/`; `WASI_SDK_PATH` overrides the location, and the build refuses an SDK whose `VERSION` differs from `wasiSDKVersion` in `cmd/wasm/cpp.go`. The lock records `clang++ --version` and the SDK and wasi-libc versions. CI only checks hashes.

## UI (`web/demos/<slug>/ui.js`, this repo)
- `export async function mount(el, demo)`: render into `el`; resolve only after the first real output is on screen. `demo.call(method, params)` returns a Promise of the result object and rejects with an Error on `{"error"}`, a crash or a 30 s timeout.
- Vanilla ES modules and DOM only. Set text with `textContent`, never `innerHTML` with data from the binary. SVG via `createElementNS`, or `<canvas>`.
- CSP: no inline `<style>` or `style="..."` attributes. Use classes from `web/assets/demo.css`, which every demo page links and home panels and the live wall load before mounting (a form control is a `<label class="demo-field">` holding a `<span class="demo-label">` and its input, so every demo's fields match); a row of output values can be a `.cells` list, mono cells on the panel's hairline ground, or a `web/demos/<slug>/ui.css` the module adds as a `<link>`. Setting `el.style.prop` from JS is allowed.
- Receipt: the last element of the UI is a `<p class="demo-out">` line (sunken mono, `aria-live="polite"` when it changes on a run) that states the real work the binary did and a time measured with `performance.now()` around the RPC call(s), updated on each run, in a sentence written for that demo: "edgecache's engine has answered 4 requests and sent 2 to the origin; replaying the run on a fresh engine at each step took 4 calls, 10 requests and 18 ms." Lowercase-led, one line, no number that did not come from the binary or the clock, and every count pluralised from its value ("1 call", "2 calls"). No stock tail such as "in your browser": every demo runs there, and nineteen receipts ending alike read as a template.
- Stat blocks use the shared `.cells stack` list, one `<li>` per stat with the label above the value (first `<span>` the label, drawn in `--text-3`; second the value). A legend is a `.demo-legend` (mono `--t-label`, `--text-2`); the demo styles only its swatches. Colours come from the demo tokens, mixed with `color-mix()` where a tint is needed; no literal colours, except inside a rendered image (the raytracer's pixels). Labels are lowercase, with no letter-spacing or uppercase.
- Accessible: real `<button>`/`<input>` with labels, keyboard-usable, `aria-live` for results that change. Respect `prefers-reduced-motion` (no auto-play animation when it is set).
- Works at 390 px wide without horizontal page scroll (wide charts scroll inside their own box). Works in light and dark, chosen by the system or the header switch: a canvas that reads tokens must redraw on both `matchMedia("(prefers-color-scheme: dark)")` change and the window's `themechange` event, and a `ui.css` that needs its own dark values states them under `@media (prefers-color-scheme: dark) { :root:not([data-theme=light]) … }` and again under `:root[data-theme=dark] …`. Use only these tokens from site.css, which follow the scheme: `--bg`, `--surface`, `--sunken` (wells, chart backgrounds), `--line`, `--line-strong`, `--control-line`, `--text`, `--text-2` (secondary text), `--text-3` (labels), `--accent`, `--accent-tint`, `--block` and `--on-block` (selected state and primary keys, as in site.css), `--signal` (the one hot mark), `--live`, `--danger`, `--mono`, `--sans`, `--t-label` (the 11 px label size), `--r-1` (0 since V12: the panel is square). Other names in site.css may change without notice; a demo may define its own properties (e.g. `--rl-gcra`) in its ui.css. The build fails on any other name (`DemoTokens` in internal/site/check.go).
- Budget: 60 KiB for `ui.js`.
- Home reel: every live demo has a showcase in `internal/site/showcase.go` and a recorded clip in `web/reel/`. Changing `ui.js`, `ui.css`, the showcase or the pinned binary makes the clip stale and fails the build: run `go run ./cmd/reel <slug>` and commit `web/reel`.

## Frame (site-owned: `templates/project.html`, `web/assets/demo.js`)
- The site renders the frame: title bar, start button, size, download progress, error state and retry. `ui.js` never builds its own loader or error box.
- On a project page the frame sits in the dark head and may start on its own (`data-autostart`, gated like the home stage), so `mount` must not assume a click: no `autofocus`, no scrolling the page, no sound. Until ready the frame shows the recorded clip (`.ph-screen`), which is removed on ready.
- `mount` runs only after the binary is ready. If it throws, the frame shows the message and a "Try again" button that clears the mount and starts a fresh worker, so `mount` must cope with being called again on an empty `el`.
- A box that scrolls sideways (wide table or chart) needs keyboard access: after `mount` the frame gives any overflowing `overflow-x: auto|scroll` element in the mount `tabindex="0"`, `role="region"` if it has no role, and `aria-label="Scrollable area"` if it has no label. Give the box your own `aria-label` naming what scrolls (e.g. "Request log"); e2e runs axe on every demo.
- After `mount` resolves from a click, focus moves to the mount itself (`tabindex="-1"`), so the next Tab reaches the first control: put the main control first. Never `autofocus` a field: a focused text input can raise a phone's keyboard.
- Hooks for tests: the section carries `data-demo-ready` or `data-demo-error`, and `data-demo-loaded` with the decompressed bytes received; project pages also carry `data-bytes` (the raw size from the lock).

## Lock and page
1. Commit and push the bridge in the project repo; its gate must be green.
2. Add `{"slug", "kind"?, "repo", "pkg": "./cmd/webdemo", "siblings"?}` to `demos.lock.json`, then `go run ./cmd/wasm pin <slug> <sha>` and `make wasm`.
3. Set `demo: live` in `content/projects/<slug>.md`; replace its `## Planned demo` section with `## How the demo works`, saying what the demo shows.
4. Add tries to `ShellTries` in `internal/site/shell.go`: calls `try <slug>` runs in the terminal, each a method and optional JSON params. When a demo's RPC changes, its tries must keep working.
5. Add the slug to `demoChecks` in `e2e/e2e_test.go` with at least one expression that proves real output from the binary rendered.
6. `make gate && make e2e`, then look at `e2e/out/projects-<slug>-*.jpg`.

## Home stage (site-owned: `internal/site/stage.go`)
The home stage runs the raytracer demo with `site.HomeStage` and shows `web/reel/stage.webp` until it renders. The build fails when the raytracer lock entry or `HomeStage` changes without a new poster: run `go run ./cmd/stage` (needs Chrome and ffmpeg) and commit `web/reel`. e2e `stageCheck` waits for live passes and measured dials; `sceneCheck` switches to the glass sphere and waits for it to render. `site.StageScenes` must name scenes the raytracer demo offers, under its labels (`TestStageScenes`).
